## 总体判断

**这个仓库现在还不是一个开源项目，它是一个"带 MIT 许可证的私有仓库"。** 内部卫生（依赖许可证、密钥、.gitignore、changelog 纪律）是达标的；外发面（可发现性、许可证正文、发布身份、包名）有 3 条阻塞级问题，任意一条都会让外人无法安装或无法合法复用。

好消息是这些全部是可机械验证的元数据问题，不需要动业务代码。本轮所有数字来自实际命令，未做估算。

## 方案

按可独立验收切 5 个 PR；PR-1/2/3 有先后依赖（先定身份，再定名字，再写文档）。

### PR-1 身份与可发现性（解 F1、F3、F13）

1. 拍板 npm 身份：确认 `yoki9904` 是否拥有 `yoki` scope。没有则二选一——把 8 个包改名到已拥有的 scope，或在 npm 开一个名为 `yoki` 的 org 并把 yoki9904 加进去。
2. 统一对外署名为一个身份（`yokii89` 或 `yoki9904`，写进 LICENSE / `author` / `repository`），并在 `packages/yoki-ui/LICENSE` 保留 Phoobobo 的原始声明作为上游致谢。
3. 把 GitHub 仓库设为 public（或改名后更新全部 manifest 与 README 的 URL）。
4. 决定个人邮箱是否要进公开历史；要清就用新 orphan 分支首发，或 `git filter-repo` 换 noreply 邮箱。
5. 6 个 `@yoki/*` 包补 `publishConfig.access: "public"`。

### PR-2 许可证与社区文件（解 F6、F7）

1. 给缺的 7 个包各放一份 `LICENSE`（与根同文，版权行按 PR-1 的结论）。
2. 写根 `README.md`：项目是什么、`pi` 是什么、9 个扩展各自一句话、可用的安装方式（只写在 PR-1 之后真实可装的那条）、从源码安装的路径、许可证与致谢。
3. 补 `SECURITY.md`（漏洞上报渠道）、`CONTRIBUTING.md`（直接写清 husky 两道钩子 + `npm run check` + `npm run coverage` 的门槛和 `.npmrc` 的 `legacy-peer-deps` 约定）。

### PR-3 发布面整形（解 F2、F8、F9、F10、F14）

1. `packages/yoki-newapi` 改名避让 `ttimasdf` 的在世包（建议并入 `@yoki/*`），并改掉 `index.ts:8` 的安装指引。
2. 给缺 `files` 的 6 个可发布包补白名单（源码 + `README.md` + `LICENSE` + `CHANGELOG.md` + `!**/*.test.ts`），把 `AGENTS.md`/`BACKLOG.md` 从 `pi-telegram-main` 的 `files` 里摘掉；删掉 `yoki_ui` 里不存在的 `assets`。第 7 个缺项 `yoki-test-utils` 走下面的 `private: true`，不用白名单。
3. `yoki-web-tools` 让 `pi.image` 指向一个不被排除的路径（如 `docs/cover.png` → `assets/cover.png`），或从排除规则里放行该文件。
4. `yoki-test-utils` 加 `"private": true`；根 `package.json` 加 `"private": true`。
5. `pi-telegram-main` 的 `latest` 改成与其余包一致的 `^22.19.19` / `^6.0.3`。

### PR-4 依赖安全（解 F4）

1. `packages/pi-telegram-main` 的 override 由 `undici 8.5.0` → ≥8.10.2、`protobufjs 7.6.4` → 7.6.5，再复测；`shx`/`vitest` 的 advisory 走升级。
2. 若某条 advisory 只有 breaking 修法，就在文档里显式记录"接受 + 理由"，不要留空。

### PR-5 门禁（解 F5、F11、F12）

1. 恢复一个最小 CI：`npm ci` → `npm run check` → `npm run coverage`（Node 22/24 matrix），把完整的 `npm audit --omit=dev` 作为非阻塞告警起步。
2. `scripts/release.mjs` 增加发布前置校验：包名是否与 registry 冲突、scoped 包是否带 `access: public`、`LICENSE`/`README`/`CHANGELOG` 是否齐、`pi.image` 是否真在 tarball 里。缺项直接 fail。
3. 补齐 4 个缺失的 `CHANGELOG.md`，并把 `getChangelogs()` 从"静默跳过"改成"缺文件即报错"。

## 风险与回退

- **仓库转 public 不可逆**：F13 的个人邮箱、F2 的撞名、以及全部 README 死链会在公开瞬间被索引。建议顺序固定为 PR-1 拍板 → PR-2/3 落地 → 最后一步才开 public。
- **改包名有下游成本**：`pi-provider-newapi` 改名会牵动 `package.json:10-11` 的 `--workspace=pi-provider-newapi` 脚本、`vitest.config.ts`、以及 README/CHANGELOG 里的旧名字。可全局检索一次改齐，回退就是 revert 单个 commit。
- **升级 undici/protobufjs 可能改变 pi-coding-agent 行为**：`packages/pi-telegram-main` 的 override 是为收敛嵌套而钉的，解除钉版后需重跑 `npm run coverage` 与 telegram 的 smoke，失败则保留旧钉并在 PR-4 第 2 项写下接受理由。
- **补 `files` 白名单可能漏打运行时文件**：这些包发布的是 `.ts` 源码（`exports` 直指 `./index.ts`），漏项会让 `pi install` 后加载失败。验收时逐个 `npm pack --dry-run` 对比 `exports`/`pi.extensions` 路径。
